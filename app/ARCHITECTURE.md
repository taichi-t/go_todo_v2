# アプリケーションアーキテクチャ設計

このドキュメントでは、アプリケーションのアーキテクチャ設計について説明します。

## アーキテクチャの概要

このアプリケーションは、以下の設計原則に基づいて実装されています：

- クリーンアーキテクチャの採用
- 依存性逆転の原則（DIP）の適用
- コンポーネントベースの設計

## ディレクトリ構造と役割

```
app/
├── components/           
├── application/              # アプリケーション層
│   ├── usecase/             # ユースケースの実装
│   │   └── gql/            # GraphQLユースケース
│   └── validator/          # バリデーションロジック
│
├── domain/                  # ドメイン層
│   ├── entity/             # エンティティ定義
│   │   └── db/            # DBエンティティ
│   ├── service/           # ドメインサービス
│   └── vo/               # 値オブジェクト
│
├── adapter/                # インターフェース・アダプター層
│   ├── gql/              # GraphQLリゾルバー
│   └── db/               # DBインターフェース
│
└── infra/                 # インフラストラクチャ層
    └── db/               # DBの実装
```

## 各層の責務

### 1. アダプター層 (`adapter/`)

外部とのインターフェースを提供：

- `gql/`: GraphQL APIインターフェース
  - リゾルバーの実装
  - モデル定義
  - スキーマ定義
  - 必要なrepository, domain serviceをNewしてUsecaseをRunする
- `db/`: データベースとのインターフェースを定義
  - インターフェースの定義のみを行い、実装は`infra`層で行う

### 2. アプリケーション層 (`application/`)

ユースケースを実装：

- `usecase/`: ビジネスロジックのオーケストレーション
  - 各ドメイン（例：`todo/`）ごとにディレクトリを分割
  - ユースケースは技術的実装から独立
- `validator/`: バリデーションロジック
- トランザクション管理

### 3. ドメイン層 (`domain/`)

ビジネスロジックの中核：

- `entity/`: ビジネスエンティティの定義
  - `db/`: sqlboiler構造体を埋め込んだDBエンティティ
- `service/`: 複数のエンティティを跨ぐような共通処理を定義
  - 複数のユースケースで共有される処理を集約
  - はじめはユースケース層で実装して、共通化の必要がある場合domain/serviceに移動する
- `vo/`: 値オブジェクトの定義

### 4. インフラストラクチャ層 (`infra/`)

技術的な実装を担当：

- `db/`: `adapter/db`で定義されたインターフェースを満たす実装を提供
  - データベースアクセスの具体的な実装

## 依存関係の方向

```
外部 → アダプター層 → アプリケーション層 → ドメイン層 ← インフラストラクチャ層
```

重要な原則：

1. 内側の層は外側の層を知らない
2. 外側の層は内側の層に依存する
3. インターフェースはドメイン層で定義
4. ユースケースは技術的実装から独立

## 設計上の注意点

1. **ドメインロジックの集中**
- ビジネスロジックはドメイン層に集中させる
- プレゼンテーション層やインフラ層にビジネスロジックを書かない

2. **依存性の注入**
- 依存関係は外側から注入する
- テスト時にモックに置き換えられるようにする

3. **トランザクション管理**
- トランザクションはユースケース層で制御
- リポジトリは単一の操作に集中

4. **エラーハンドリング**
- 各層で適切なエラーハンドリング
- ドメインエラーとインフラエラーを区別

## ユースケースの設計原則

1. **単一責任の原則**
- 各ユースケースは1つの具体的なビジネスケースに対応

2. **技術的独立性**
- GraphQLやREST APIなどの技術的詳細から独立

## バリデーションの設計原則

各層でのバリデーションは以下の原則に従って実装します：

### 1. Adapter層のバリデーション（基本的にGraphQLのschemaを定義している場合ここのバリデーションは不要）
- 入力データの構文的な検証を担当
- リクエストパラメータの型チェック
- 必須項目の検証
- データ形式の基本的な検証

### 2. Application層のバリデーション
- ユースケース固有のビジネスルールを検証
- 複数フィールド間の相関チェック
- ユーザーの権限チェック
- トランザクションの整合性確認

### 3. Domain層のバリデーション
- ドメインの不変条件を保証
- エンティティの整合性チェック
- 値オブジェクトのバリデーション
- ビジネスルールの検証

### バリデーションの実行順序
1. Adapter層で基本的なデータ形式を検証
2. Application層でユースケース固有のルールを検証
3. Domain層でビジネスルールと不変条件を保証

### バリデーションの設計指針
- 各層の責務に応じた適切なバリデーションの実装
- バリデーションロジックの重複を避ける
- エラーは発生した層で適切に捕捉し、上位層に伝播
- テスタビリティを考慮した実装
